# Конституция BC Scanner Android

## Основные принципы

### I. SOLID Design

Архитектура строится на принципах SOLID, и это не пожелание, а требование к любому коду:

- **SRP**: каждый класс и модуль имеет ровно одну причину для изменения.
- **OCP**: поведение расширяется добавлением нового кода (новые источники данных, типы
  сканеров, форматы), а не правкой существующих ветвлений.
- **LSP**: реализации не нарушают контракты своих интерфейсов и базовых типов.
- **ISP**: интерфейсы узкие и специфичны для клиента; не создаются «универсальные» на все случаи.
- **DIP**: зависимости направлены на абстракции. Работа с BLE, камерой, хранилищем и сетью
  скрыта за интерфейсами; конкретные реализации внедряются извне.

**Обоснование**: платформенный код Android (BLE, камера, разрешения) невозможно полноценно
тестировать в изоляции. Инверсия зависимостей и разделение ответственности позволяют подменять
платформу моками, изолировать изменения и развивать функциональность без регрессий.

### II. Test-First (NON-NEGOTIABLE)

Разработка ведётся строго по циклу **Red → Green → Refactor**:

- Сначала пишется падающий тест, описывающий требуемое поведение.
- Затем — минимальная реализация, делающая тест зелёным.
- Затем — рефакторинг без изменения поведения.

Правила:

- Вся бизнес-логика покрыта unit-тестами; платформенные зависимости подменяются через интерфейсы.
- Коммит, меняющий поведение, обязан включать соответствующий тест.
- Изменение поведения без теста не допускается к слиянию.

**Область действия**: принцип распространяется исключительно на Android-приложение
(`bc_scanner_android`). Приложение для FlipperZero (`bc_scanner_emulate`, язык C) вне области
действия принципа: его код проверяется сборкой `fbt` и ручной проверкой на реальном устройстве,
обязательные unit-тесты для него не требуются.

**Обоснование**: тесты — это исполняемая спецификация и страховка от регрессий при рефакторинге.
Без обязательного TDD требования SOLID и простого UI быстро деградируют.

### III. Simple UI

Интерфейс остаётся намеренно простым:

- Минимум экранов и элементов управления; ключевые функции доступны за 2–3 действия.
- **YAGNI**: экраны, настройки и «заготовки на будущее» не добавляются, пока нет реальной
  потребности.
- UI не содержит бизнес-логики: он только отображает состояние и транслирует события (MVVM).
- Состояние экрана однозначно: загрузка, пусто, ошибка, успех — все состояния обработаны.

**Обоснование**: простая поверхность уменьшает число багов, ускоряет разработку и упрощает
проверку. Сложность вводится только под подтверждённую задачу.

### IV. Permissioned Hardware Access

Доступ к камере и Bluetooth осуществляется только безопасным и предсказуемым образом:

- Камера и Bluetooth (BLE) используются исключительно через runtime-разрешения, запрашиваемые
  в момент фактической необходимости, а не при старте приложения.
- При отказе в разрешении приложение деградирует корректно (без падений) и объясняет, зачем
  нужно разрешение и как его выдать.
- Работа с BLE и камерой привязана к жизненному циклу: сканирование и предпросмотр стартуют и
  останавливаются в `onStart`/`onStop`, ресурсы (колбэки, сенсоры, потоки) освобождаются.
- Соединение BLE и поток кадров не блокируют главный поток.

**Обоснование**: аппаратные API Android чувствительны к разрешениям и жизненному циклу. Нарушение
этих правил ведёт к отказам, утечкам и отклонению в магазине приложений.

### V. One Commit = One Task

Дисциплина коммитов строгая:

- Один коммит реализует ровно одну задачу и содержит только изменения, необходимые для неё.
- Каждый коммит должен собираться и проходить тесты.
- Сообщение коммита описывает задачу в повелительном наклонении и на английском языке
  (например, `Add BLE device scan screen`).
- Несвязанные изменения (рефакторинг, форматирование, правки документации) выносятся в отдельные
  коммиты.

**Обоснование**: атомарные коммиты упрощают ревью, точечный откат и трассировку «требование →
реализация → тест». Это прямое следствие принципа «одна задача за раз».

## Технологический стек и ограничения

- **Язык**: только Kotlin, идиоматичный (корутины/Flow вместо блокирующих вызовов, без Java-кода
  в новом коде).
- **Платформа**: нативный Android; `minSdk` = 26 (Android 8.0).
- **Bluetooth**: только BLE (Bluetooth Low Energy).
- **Камера и штрихкоды**: CameraX + ML Kit.
- **UI**: Jetpack Compose предпочтителен; окончательный выбор фиксируется в плане фичи.
- **Зависимости**: из официальных и поддерживаемых источников; количество библиотек
  минимизируется (YAGNI). Каждая новая зависимость обосновывается.
- **Языковая политика**: идентификаторы, комментарии в коде и сообщения коммитов — на английском;
  документация, спецификации и тексты конституции — на русском.

## Рабочий процесс разработки и контроль качества

- Изменения проходят путь Spec Kit: **спецификация → план → задачи → реализация**.
- TDD-цикл обязателен для каждой задачи Android-приложения; код FlipperZero проверяется сборкой
  `fbt` и ручной проверкой на устройстве (см. Принцип II, «Область действия»).
- Перед коммитом: сборка проходит, тесты зелёные, линтер/форматтер без ошибок.
- Изменения, затрагивающие разрешения или работу с железом (BLE, камера), проверяются на реальном
  устройстве, а не только на эмуляторе.
- Ревью проверяет соответствие принципам I–V; сложность, не оправданная задачей, отклоняется.

## Governance

- Конституция имеет приоритет над остальными практиками. При конфликте правил приоритет у неё.
- **Поправки**: вносятся только через команду обновления конституции, с фиксацией новой версии и
  даты и с кратким обоснованием изменения.
- **Версионирование (SemVer)**:
  - **MAJOR** — удаление или переопределение принципа, несовместимое с прежними правилами.
  - **MINOR** — добавление нового принципа или раздела, либо существенное расширение guidance.
  - **PATCH** — уточнения формулировок, исправление опечаток, не меняющие смысл.
- **Проверка соответствия**: каждый план фичи содержит раздел Constitution Check; каждый PR/ревью
  подтверждает соблюдение принципов. Нарушения фиксируются и устраняются до слияния.
